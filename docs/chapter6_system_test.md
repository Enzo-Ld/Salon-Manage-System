# 第5章 系统测试及使用说明

## 5.1 系统测试报告

### 5.1.1 测试的目的及原则

系统测试是软件开发完成后验证系统功能、业务流程和运行质量的重要环节。本文设计并实现的“基于 Spring Boot 的美容美发预约管理系统”采用前后端分离架构，后端基于 Spring Boot 3.4.4、Java 17、Spring Security、JWT、MyBatis-Plus、MySQL、Redis、WebSocket 和 Knife4j 实现，前端基于 Vue3、TypeScript、Vite、Element Plus、Pinia、Vue Router、Axios 和 ECharts 实现。系统包含普通用户端、技师端和管理员端，业务范围覆盖登录注册、角色权限、服务预约、技师推荐、排班、请假考勤、预约支付、商城订单、钱包充值、在线沟通、消息通知、AI 顾问和后台统计等功能。

本系统测试的主要目的是验证系统是否达到毕业设计预期目标，具体包括：验证各功能模块是否能够正常完成业务操作；验证前端页面、后端接口和数据库数据是否保持一致；验证不同角色之间的权限隔离是否有效；验证预约冲突、排班冲突、请假冲突、库存不足、余额不足等异常场景能否被系统正确拦截；验证系统在常规使用流程下是否具有较好的稳定性和可用性。

本系统测试遵循以下原则：

1. 功能覆盖原则。测试内容应覆盖系统已经实现的主要功能模块，保证普通用户、技师和管理员的核心业务流程均经过验证。
2. 真实性原则。测试内容必须以项目代码中已经实现的页面、接口和服务逻辑为依据，不对系统未实现的功能进行扩展描述。
3. 角色隔离原则。分别使用普通用户、技师和管理员账号进行测试，验证不同角色只能访问其权限范围内的页面和接口。
4. 数据一致性原则。涉及预约、支付、订单、钱包、排班、请假、考勤等数据变更时，需要验证页面显示、接口返回和数据库状态是否一致。
5. 异常校验原则。测试不仅覆盖正常业务流程，也覆盖错误密码、未登录访问、越权访问、重复预约、重复排班、库存不足、余额不足等异常场景。
6. 可操作性原则。测试过程应尽量贴近真实用户使用习惯，关注页面提示、表单校验、按钮状态、分页筛选、弹窗交互和图表展示效果。

### 5.1.2 测试过程及结果

#### (1) 登录注册模块的测试过程及结果

登录注册模块主要测试用户注册、用户登录、登录失败提示和登录状态保持功能。测试时，首先进入注册页面，填写用户名、密码、手机号等信息并提交，系统能够创建普通用户账号。随后进入登录页面，使用正确账号密码登录，前端调用登录接口，后端校验成功后返回 JWT 访问令牌，前端将 token 保存到 `localStorage`，并通过 Pinia 状态管理模块加载当前用户信息。

继续测试错误密码和不存在账号登录场景。输入错误密码时，系统不会进入业务页面，并提示账号或密码错误；输入不存在的账号时，后端返回登录失败信息。刷新页面后，只要本地 token 有效，系统能够重新加载当前用户信息，保持登录状态。

测试结果表明，登录注册模块能够正常完成用户注册、登录认证、失败提示和登录状态恢复，满足系统基础身份认证要求。

#### (2) 角色权限模块的测试过程及结果

角色权限模块主要测试普通用户、技师和管理员三类角色的页面访问控制。系统在 `frontend/src/router/index.ts` 中为用户端、技师端和管理员端页面配置了 `roles` 元信息，并通过路由守卫判断当前用户是否具备访问权限。

测试时，普通用户登录后访问 `/services`、`/appointments`、`/shop`、`/wallet` 等用户端页面，系统允许访问；当普通用户手动访问 `/admin/dashboard` 或 `/tech/dashboard` 时，系统自动跳转到普通用户默认页面。技师账号登录后可以访问 `/tech/dashboard`、`/tech/appointments` 和 `/tech/leaves`，但不能访问管理员后台页面。管理员账号登录后可以访问 `/admin/dashboard`、`/admin/schedules`、`/admin/users` 等后台页面。未登录状态下直接访问任意业务页面时，系统跳转到登录页面。

测试结果表明，前端路由权限控制和后端 Spring Security 权限校验能够协同工作，不同角色之间的页面访问边界清晰，能够防止普通用户越权进入后台管理页面。

#### (3) 服务浏览与收藏模块的测试过程及结果

服务浏览与收藏模块主要测试用户端服务列表页面。测试时，普通用户进入 `ServiceListView.vue` 页面，系统能够加载服务分类、服务项目、技师列表和用户已收藏服务编号。服务卡片能够展示服务名称、分类、价格、服务时长、简介和图片等信息。

在筛选测试中，输入服务名称或简介关键字后，页面能够根据关键字过滤服务项目；选择服务分类后，页面仅展示对应分类下的服务。点击收藏按钮后，前端调用收藏接口，服务收藏状态发生切换；再次点击同一按钮后，系统取消收藏。

测试结果表明，服务浏览、分类筛选、关键字搜索和服务收藏功能均能正常使用，前端页面与后端收藏状态保持一致。

#### (4) 服务预约模块的测试过程及结果

服务预约模块主要测试预约弹窗、预约日期选择、技师选择、可预约时间段查询和预约创建功能。用户点击服务卡片后，系统打开预约窗口。用户选择预约日期后，前端调用 `/api/appointments/available-slots` 接口，后端根据服务时长、技师排班、请假记录和已有预约记录计算可预约时间段。

测试正常预约流程时，用户选择服务项目、预约日期和可用时间段后提交预约，系统成功生成预约单。预约创建后，预约状态为 `CREATED`，支付状态为 `UNPAID`，页面跳转到“我的预约”页面提示用户继续支付。

测试异常预约流程时，选择早于当前时间的预约时间，系统提示预约时间不能早于当前时间；选择无排班技师或已请假技师，系统拒绝创建预约；选择已经被有效预约占用的时间段，系统提示该时间段技师已被预约。

测试结果表明，服务预约模块能够正确完成预约创建流程，并能有效处理时间无效、排班不可用、请假冲突和预约冲突等异常情况。

#### (5) 技师推荐模块的测试过程及结果

技师推荐模块主要测试用户未手动指定技师时系统自动推荐技师的功能。测试时，用户在预约弹窗中仅选择服务项目、预约日期和时间段，不选择具体技师。系统根据当前服务项目查询支持该服务且状态为启用的技师，然后过滤不在排班内、处于请假状态或已有预约冲突的技师。

在推荐结果测试中，系统会根据技师评分和当天负载计算推荐分，并选择推荐分最高的技师返回给前端。若当前时段没有可用技师，系统返回无可推荐技师提示。

测试结果表明，技师推荐模块能够结合服务能力、排班、请假、预约冲突、技师评分和当天负载进行推荐，推荐结果符合系统业务规则。

#### (6) 预约支付模块的测试过程及结果

预约支付模块主要测试用户在“我的预约”页面对待支付预约进行支付的流程。用户点击支付按钮后，系统弹出支付窗口，可选择余额、微信或支付宝等支付方式。

测试余额支付时，若用户钱包余额充足，系统扣减用户钱包余额，生成支付记录，并将预约支付状态更新为 `PAID`，预约业务状态更新为 `PENDING`。若余额不足，系统提示余额不足，预约状态不发生变化。测试在线支付时，系统创建业务类型为 `APPOINTMENT` 的支付单，支付成功后由后端支付服务同步更新预约支付状态、支付单号和支付时间。

测试结果表明，预约支付模块能够正常完成支付单创建、余额扣款和支付成功后的业务状态更新。支付失败或余额不足时，系统不会错误更新预约状态。

#### (7) 预约状态流转与评价模块的测试过程及结果

预约状态流转模块主要测试技师或管理员对预约状态的处理过程。预约支付成功后状态为 `PENDING`，技师可以确认预约，使状态变为 `APPROVED`。后续根据服务进度，预约可依次变为 `WAIT_SERVICE`、`IN_SERVICE` 和 `COMPLETED`。

测试非法状态流转时，尝试将 `PENDING` 状态直接修改为 `COMPLETED`，后端拒绝该操作。预约完成后，用户可以提交评分和评价内容；若预约尚未完成，系统不允许提交评价。用户取消已支付预约时，系统会进入退款处理逻辑；取消未支付预约时，系统直接关闭预约。

测试结果表明，预约状态流转符合系统定义的状态机规则，非法状态变更能够被拦截，评价功能仅在预约完成后开放。

#### (8) 排班管理模块的测试过程及结果

排班管理模块主要测试管理员端 `AdminScheduleView.vue` 页面。管理员进入排班管理页面后，系统能够展示技师总数、今日排班、本周排班和已批准请假数量。

手动排班测试中，管理员选择技师、日期范围、工作日、上班时间和下班时间后提交，系统能够批量生成排班记录。自动排班测试中，管理员设置候选技师、日期范围、工作日、每日排班人数和覆盖策略后，系统生成自动排班预览，显示计划排班人数、实际生成数量和缺口数量。确认应用后，系统将无冲突的排班写入数据库。

异常测试中，为同一技师添加同一天重叠时间段排班时，系统提示排班冲突；删除已有有效预约占用的排班时，系统拒绝操作。

测试结果表明，排班管理模块能够正常完成手动排班、自动排班预览和自动排班应用，并能够防止重叠排班和破坏已有预约的排班调整。

#### (9) 请假管理模块的测试过程及结果

请假管理模块主要测试技师请假申请和管理员审批流程。技师登录后进入 `TechLeaveView.vue` 页面，填写请假开始时间、结束时间和请假原因后提交，系统生成状态为 `PENDING` 的请假申请。

管理员进入请假审批页面后，可以查看待审批请假申请。审批通过时，后端检查该技师在请假时间段内是否存在其他已批准请假或有效预约；如果没有冲突，请假状态变为 `APPROVED`；如果存在预约冲突，系统提示需要处理冲突预约后再审批。管理员驳回请假时，需要填写审批说明，系统将请假状态更新为 `REJECTED`。

测试结果表明，请假管理模块能够完成请假申请、审批通过、审批驳回和冲突校验，能够避免请假记录与已有预约产生履约冲突。

#### (10) 考勤打卡模块的测试过程及结果

考勤打卡模块主要测试技师签到和签退流程。技师进入工作台后，系统加载当天排班、当前请假状态和已有考勤记录。若当天存在有效排班且当前不在请假时间段内，技师可以点击签到，系统写入签到时间并将考勤状态设置为 `ON_DUTY`。

技师完成工作后点击签退，系统校验当天已经签到且尚未签退，然后写入签退时间，将考勤状态更新为 `OFF_DUTY`。异常测试中，若当天没有排班，系统不允许签到；若当前处于已批准请假时间段内，系统提示不能打卡；若未签到直接签退，系统提示需要先签到。

测试结果表明，考勤打卡模块能够结合排班和请假状态进行校验，签到、签退和异常限制逻辑正确。

#### (11) 商品商城与购物车模块的测试过程及结果

商品商城与购物车模块主要测试商品浏览、筛选、收藏、加入购物车和购物车数量调整功能。用户进入商城页面后，系统加载商品分类和上架商品。用户可以按商品名称、分类进行筛选，也可以查看商品详情、收藏商品或取消收藏。

用户点击加入购物车后，系统将商品加入购物车。进入购物车页面后，用户可以勾选商品、修改数量、删除商品，页面会根据商品数量实时计算合计金额。若用户未勾选商品直接提交订单，页面提示需要先勾选要结算的商品。

测试结果表明，商品商城页面展示正常，购物车增删改和金额计算正确，用户可以完成从商品浏览到购物车结算前的完整流程。

#### (12) 商品订单与售后模块的测试过程及结果

商品订单模块主要测试订单创建、库存扣减、订单支付、发货、确认收货和售后申请。用户在购物车中勾选商品并选择收货地址后提交订单。后端校验收货地址归属，并对商品库存使用 Redis 分布式锁进行控制。库存充足时，系统扣减库存并生成订单和订单明细；库存不足时，系统返回库存不足提示。

订单支付成功后，订单状态变为 `PAID`。管理员进入订单管理页面填写物流公司和物流单号后发货，订单状态变为 `SHIPPED`。用户收到商品后确认收货，订单状态变为 `COMPLETED`。售后测试中，用户提交售后申请后，订单售后状态变为 `REQUESTED`；管理员审核通过后，系统处理退款并恢复库存；管理员驳回后，售后状态变为 `REJECTED`。

测试结果表明，商品订单模块能够完成下单、库存扣减、支付、发货、收货和售后处理流程，订单状态变化符合业务规则。

#### (13) 钱包充值模块的测试过程及结果

钱包充值模块主要测试余额展示、充值活动、充值支付和交易流水。用户进入钱包页面后，系统展示当前余额、累计充值、累计赠送和钱包流水。用户选择充值金额、充值活动和支付方式后，系统创建钱包充值支付单。

支付成功后，系统将充值金额和活动赠送金额写入钱包余额，并生成充值流水和赠送流水。测试余额支付订单时，若余额充足，系统扣减余额并生成消费流水；若余额不足，系统提示余额不足，不更新订单支付状态。

测试结果表明，钱包充值、活动赠送、余额消费和流水记录功能正常，钱包余额能够随充值、支付和退款等业务正确变化。

#### (14) 在线沟通模块的测试过程及结果

在线沟通模块主要测试聊天会话创建、消息发送、消息保存和 WebSocket 推送。用户可以从预约页面进入聊天页面，系统会携带预约编号、服务项目、预约时间和技师信息作为沟通上下文。用户输入消息并发送后，后端查找或创建聊天会话，保存聊天消息，更新会话时间，并通过 WebSocket 推送给接收方。

技师登录后进入聊天页面，可以查看用户发送的消息并进行回复。聊天列表中能够展示最近会话和最新消息，消息详情按照发送时间展示。

测试结果表明，在线沟通模块能够满足用户与技师之间的基本沟通需求，消息记录保存和实时推送功能正常。

#### (15) 消息通知模块的测试过程及结果

消息通知模块主要测试系统通知生成、未读数量统计、标记已读和清理已读通知。系统在预约支付成功、预约状态变更、订单支付、订单发货、售后申请、请假审批等关键业务节点调用通知服务生成通知记录。

用户进入通知页面后，可以查看通知列表、通知分类、通知内容和未读状态。点击某条通知后，系统将该通知标记为已读，未读数量减少。点击全部已读后，系统批量更新通知状态。点击清除已读后，系统删除已读通知。

测试结果表明，消息通知模块能够覆盖系统主要业务事件，未读数量和通知状态更新正确。

#### (16) AI 顾问模块的测试过程及结果

AI 顾问模块主要测试用户咨询、图片上传、历史会话、服务推荐和商品推荐功能。用户进入 `AiConsultView.vue` 页面后，可以输入护理需求，也可以上传图片作为上下文。系统上传图片后返回 `/uploads/ai-consult/` 路径下的图片地址。

当用户输入“我想放松，先做什么服务”“日常护理应该买什么商品”“预算有限，服务和商品怎么搭配”等内容时，系统能够识别服务意图和商品意图，并结合系统中的服务目录、商品目录返回推荐结果。若远程 AI 接口不可用，系统使用本地规则推荐，不影响基础咨询功能。用户可以查看历史会话，也可以删除历史咨询记录。

测试结果表明，AI 顾问模块能够根据用户输入生成咨询回复，并能够基于系统真实服务项目和商品数据生成推荐内容。

#### (17) 后台统计模块的测试过程及结果

## 5.2 系统使用说明

### 5.2.1 系统简介

本系统是一个基于 Spring Boot 和 Vue3 的美容美发预约管理系统，采用前后端分离架构。系统面向美容美发门店的实际业务场景，提供普通用户端、技师端和管理员端三类角色功能。

用户端主要包括登录注册、服务浏览、服务收藏、服务预约、技师推荐、预约支付、我的预约、商品商城、购物车、商品订单、钱包充值、在线沟通、消息通知和 AI 顾问咨询等功能。用户可以在线选择服务项目和预约时间，也可以在商城购买护理商品，并通过钱包或在线支付完成支付。

技师端主要包括技师工作台、预约处理、服务状态推进、请假申请、考勤打卡和在线沟通等功能。技师可以查看分配给自己的预约，确认预约并推进服务状态，也可以提交请假申请和完成上下班考勤。

管理员端主要包括后台统计、用户管理、服务分类管理、服务项目管理、技师管理、技师服务能力维护、排班管理、请假审批、商品分类管理、商品管理、订单管理、充值活动管理、评论管理、轮播图和公告资讯管理等功能。管理员可以维护门店基础数据，并通过统计图表查看商城经营情况。


### 5.2.3 系统操作说明

#### 1. 普通用户操作说明

普通用户打开系统后，首先进入登录页面。没有账号时，可以进入注册页面创建普通用户账号；已有账号时，输入用户名和密码登录系统。登录成功后，系统默认进入用户端功能页面。

用户可以进入服务列表页面查看门店服务项目。页面支持按关键字和服务分类筛选项目，用户点击服务项目后打开预约窗口，选择预约日期、技师和可预约时间段。如果用户不指定技师，系统会自动推荐合适技师。提交预约后，系统生成预约单，用户需要进入“我的预约”页面完成支付。支付成功后，预约进入待确认状态，技师确认后用户可按预约时间到店服务。服务完成后，用户可以对预约进行评价。

用户也可以进入商品商城页面浏览护理商品，将商品加入购物车，在购物车中选择商品和收货地址后提交订单。订单创建后需要完成支付，支付成功后等待管理员发货。收到商品后，用户可以在订单详情页确认收货，也可以在符合条件时提交售后申请。

用户在钱包页面可以查看余额、累计充值、累计赠送和交易流水，也可以选择充值活动和支付方式进行充值。在线沟通页面用于与技师或相关用户交流预约、商品和售后问题。AI 顾问页面支持输入护理需求或上传图片，系统会根据当前服务和商品数据给出推荐。

#### 2. 技师操作说明

技师登录后进入技师端工作台。技师可以查看自己负责的预约记录，并根据实际服务进度进行处理。对于待确认预约，技师可以确认或拒绝；对于已确认预约，技师可继续推进为待服务、服务中和已完成状态。

技师可以进入请假页面提交请假申请。填写请假开始时间、结束时间和请假原因后，系统生成待审批请假记录。请假申请需要管理员审批，审批通过后会影响该技师的排班和考勤。技师还可以在考勤功能中查看当天排班，并完成签到和签退操作。若当天没有排班或当前处于已批准请假时间段，系统会限制打卡。

技师可以使用在线沟通功能与用户交流预约事项。当技师确认预约后，系统还会自动向用户发送预约提醒消息，方便用户了解服务时间和到店安排。

#### 3. 管理员操作说明

管理员登录后进入后台管理端。管理员可以在后台统计页面查看商城经营统计，包括销售额、订单数、售出件数、商品销量排行和分类销售统计等。统计图表由 ECharts 展示，便于管理员掌握门店经营情况。

管理员可以维护服务分类、服务项目、技师信息和技师服务能力。新增服务项目后，用户端服务列表可以查询到该项目；新增技师并绑定服务能力后，该技师可以参与对应服务的预约和推荐。

在排班管理页面，管理员可以进行手动排班或自动排班。手动排班适合指定技师和指定日期的场景；自动排班适合批量生成某一时间范围内的排班。系统会在排班时检查请假、已有排班和预约冲突。

管理员可以在请假审批页面处理技师请假申请。若请假时间段内存在预约冲突，系统会提示管理员处理冲突后再审批。管理员还可以管理商品分类、商品信息、商品订单、订单发货、售后退款、充值活动、用户账号、评论、轮播图和公告资讯等内容。

#### 4. 系统退出说明

用户、技师或管理员使用完系统后，可以通过页面中的退出登录功能退出系统。退出后，前端会清除本地保存的 token 和当前用户信息，再次访问业务页面时需要重新登录。该机制能够避免用户离开设备后账号仍保持登录状态，从而提升系统使用安全性。
